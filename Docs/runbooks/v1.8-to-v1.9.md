# 操作手册：v1.8 → v1.9

## 演进概述

在不动有状态服务（MySQL / Redis / ProxySQL）的前提下，把 ruoyi 无状态后端从 gz-02 / gz-03 的 Docker Compose 迁移到 **gz-05 server+agent + gz-04 worker + gz-06 worker** 组成的 K3s 三节点集群，验证 Kubernetes 基础工作流（Deployment 2 副本跨 worker 分布、滚动更新、`rollout undo` 回滚、三类故障演练），并为后续 Helm / Loki 打基础。节点间 apiserver / flannel 流量强制走 Tailscale；ruoyi Pod 经 Tailscale 内网访问现有 gz-03 ProxySQL（`100.92.5.116:6033`）与 Redis Sentinel（`mymaster`）；K3s 二进制与系统镜像因 gz 节点公网受限（连不上 docker.io / GitHub）改由控制节点 bj-01 离线 airgap 分发（**实测调整，见下方 Phase 2「模块一执行实况校准」**）；kubectl 与 YAML 下发统一从 bj-01 发起。迁移验证通过后 gz-02 / gz-03 Compose 副本**停而不删**，保留 3 天只读回滚窗口。

详细设计见 [`Docs/proposals/k3s-stateless.md`](../proposals/k3s-stateless.md)，路线主题 [`k3s-stateless`](../scheme/phase-1-architecture-upgrade.md#k3s-stateless)。

> **gz-06 前置**：本主题 K3s 安装依赖新增腾讯云·广州 4C4G 常驻 worker **gz-06** 先完成 onboarding（复用 v1.8 流程）。gz-06 onboarding 作为本 runbook 的 **Phase 0**。

### Phase 1：变量 / inventory / vault 框架（框架检查点）

**① 目标说明**

写入 K3s 所需的非敏感变量（server host/port、ruoyi K3s 命名空间 / NodePort / 副本数），在 inventory 新增 K3s 分组（`k3s_server_nodes` = gz-05；`k3s_agent_nodes` = gz-04 / gz-06；`k3s_nodes` 聚合），在 vault 新增集群加入 token `k3s_token`。本 Phase 只改变量与 inventory，不部署。

**② 节点**：bj-01（100.118.69.78）

**③ 具体命令**

在 `inventory/hosts.yml` 的 `children` 段新增 K3s 分组（gz-04 / gz-05 / gz-06 已在 `managed_nodes` / `exporter_nodes`，本次叠加，**不进 `app_nodes`**）：

```yaml
    k3s_server_nodes:
      hosts:
        gz-05:
    k3s_agent_nodes:
      hosts:
        gz-04:
        gz-06:
    k3s_nodes:
      children:
        k3s_server_nodes:
        k3s_agent_nodes:
```

在 `inventory/group_vars/all.yml` 末尾追加 K3s 段：

```yaml
# ── K3s（k3s-stateless 主题，v1.9）─────────────────────────────────────────────
# server host 从 k3s_server_nodes 第一台（gz-05）的 ansible_host 派生，单一事实源。
k3s_server_host: "{{ hostvars[groups['k3s_server_nodes'][0]].ansible_host }}"  # gz-05 Tailscale IP
k3s_api_port: 6443
ruoyi_k3s_namespace: ruoyi
ruoyi_k3s_nodeport: 30080      # gz-01 Nginx upstream 指向各 K3s 节点此端口
ruoyi_k3s_replicas: 2

# ── airgap 离线安装（实测追加：gz 节点连不上 docker.io / GitHub）─────────────────
# version / arch 是唯一旋钮，其余 URL / 路径均派生；下载基址走 DaoCloud GitHub 文件代理
# （直连 release CDN 不稳、rancher-mirror 二进制/airgap 路径 404）。tag 里 '+' 转义为 %2B。
k3s_version: "v1.35.5+k3s1"
k3s_arch: "amd64"
k3s_airgap_cache_dir: "{{ lookup('env', 'HOME') }}/.cache/k3s-airgap/{{ k3s_version }}"
k3s_airgap_images_filename: "k3s-airgap-images-{{ k3s_arch }}.tar.zst"
k3s_release_base: "https://files.m.daocloud.io/github.com/k3s-io/k3s/releases/download/{{ k3s_version | replace('+', '%2B') }}"
k3s_binary_url: "{{ k3s_release_base }}/k3s"
k3s_airgap_images_url: "{{ k3s_release_base }}/{{ k3s_airgap_images_filename }}"
k3s_sha256_url: "{{ k3s_release_base }}/sha256sum-{{ k3s_arch }}.txt"
k3s_install_script_url: "https://get.k3s.io"  # 仅控制节点下载一次再分发
k3s_install_script_path: /usr/local/share/k3s/install.sh
```

把 `k3s_token` 写入 vault（随机长串；固定写入保证 agent join 幂等可重复）：

```bash
cd /opt/docker-infra

# 生成一个随机 token（仅在本地终端生成，不回显进文件历史）
K3S_TOKEN_VALUE=$(openssl rand -hex 32)

# 编辑 vault 追加 k3s_token: <值>（用 ansible-vault edit 打开后手工粘贴）
ansible-vault edit vault/secrets.yml
# 在文件中加入一行： k3s_token: "<把 $K3S_TOKEN_VALUE 的值粘进来>"

unset K3S_TOKEN_VALUE   # 清掉环境变量
```

**④ 预期输出**

```text
hosts.yml 出现 k3s_server_nodes / k3s_agent_nodes / k3s_nodes 三个分组。
group_vars/all.yml 末尾出现 K3s 段（k3s_server_host 等 5 个变量）。
vault/secrets.yml 内新增 k3s_token（保存后仍为 $ANSIBLE_VAULT;1.1;AES256 开头）。
```

          envFrom:

### Phase 8：发布能力验证（滚动更新 + 回滚）

**① 目标说明**

#     推荐先推一个内容相同但 tag 不同的临时测试镜像，或正式发布时换精确 tag。
#     另开一个终端持续打公网，观察是否出现 5xx

### Phase 9：三类故障演练 + drills 记录

**① 目标说明**

按 proposal §4 与路线图验收，做三类受控故障演练，每类观察"现象 → 用 kubectl 定位 → 恢复"，记录到 `Docs/drills/v1.9-k3s-failure-drills.md`（按 docs-workflow §7 命名约定）。演练在模块二 review 前完成，Compose 老副本在线作兜底。

**② 节点**：bj-01

**③ 具体命令**

```bash
export KUBECONFIG=~/.kube/k3s-ruoyi.yaml

# 演练 ① ImagePullBackOff：发布不存在的 tag，观察并定位
kubectl -n ruoyi set image deployment/ruoyi ruoyi={{ registry_host }}/ruoyi:nonexistent-tag
kubectl -n ruoyi get pods            # 新 Pod ImagePullBackOff
kubectl -n ruoyi describe pod -l app=ruoyi | grep -A5 -iE 'Events|Failed|Back-off'
kubectl -n ruoyi rollout undo deployment/ruoyi    # 恢复

# 演练 ② 配错 readinessProbe：临时把 probe 指向错端口，观察 rollout 卡住
#     用 kubectl patch 改 readinessProbe 端口为 9999（无监听）
kubectl -n ruoyi patch deployment ruoyi --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/tcpSocket/port","value":9999}]'
kubectl -n ruoyi rollout status deployment/ruoyi --timeout=60s    # 预期超时
kubectl -n ruoyi get pods            # 新 Pod Running 但 READY 0/1
kubectl -n ruoyi rollout undo deployment/ruoyi    # 恢复 probe

# 演练 ③ drain gz-04：Pod 迁走，验证业务可用性影响
kubectl drain gz-04 --ignore-daemonsets --delete-emptydir-data --timeout=120s
kubectl -n ruoyi get pods -o wide    # gz-04 上 Pod 被驱逐；新 Pod 只能落 gz-06 或保持 Pending，不应落 gz-05
kubectl uncordon gz-04               # 恢复调度
```

**④ 预期输出**

```text
① 新 Pod ImagePullBackOff；describe events 含 "Failed to pull image ... not found"；undo 后恢复。
② rollout status 60s 超时；新 Pod READY 0/1（readiness 失败不接流量，maxUnavailable:0 不会摘旧副本）；undo 恢复。
③ drain 后 gz-04 Pod Evicted；新 Pod 在 gz-06 起，或因 topology / 资源约束保持 Pending；不应落 gz-05（control-plane 已排除）。期间至少另一副本在线，公网可用性影响记录到 drills。
```

**⑤ 验证方法**

```bash
export KUBECONFIG=~/.kube/k3s-ruoyi.yaml
kubectl -n ruoyi get pods -o wide
kubectl get nodes                    # uncordon 后 gz-04 SchedulingDisabled 消失
```

**预期验证输出**

```text
三类演练现象均如预期，且每类都能用 kubectl describe / events / rollout status 定位根因。
Docs/drills/v1.9-k3s-failure-drills.md 记录三类实测时间线与可用性影响。
```

> **drills 记录单独提交**：`docs(drills): record v1.9 k3s failure drills`。演练只验证已有能力，不顺势改架构（docs-workflow §7 红线）。

**⑥ 回滚方式**

每个演练自带恢复步骤（`rollout undo` / `uncordon`）。演练结束确认 Deployment 回到 2 副本 `Running`、`READY 1/1`、`kubectl get nodes` 全 `Ready` 无 `SchedulingDisabled`。
