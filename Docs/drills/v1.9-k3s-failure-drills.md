## 1. 演练目标

本次演练用实测数据回答以下问题：

1. **发布不存在的 tag**：当 `set image` 指向 Registry 中不存在的 tag 时，K8s 是否只替换一个新 Pod 并使其停在 `ImagePullBackOff`、旧副本是否全程在线（`maxUnavailable:0` 生效），`rollout undo` 能否一键恢复？
2. **readinessProbe 配错**：把 readiness 探针指向无监听端口（9999）后，新 Pod 是否会停在 `READY 0/1`、`rollout status` 是否如期超时、旧副本是否因 `maxUnavailable:0` 不被摘除，`rollout undo` 能否恢复？
3. **drain worker 节点**：drain `ops-lab-gz-04` 后其上 Pod 是否被驱逐，替换 Pod 会落到 `ops-lab-gz-06`、保持 `Pending`，还是错误地落到 control-plane `ops-lab-gz-05`？单副本窗口期有多长？`uncordon` 后是否自动恢复跨节点分布？
4. **reboot worker 节点（冷启动自愈）**：突发 `reboot` 一台 worker（`ops-lab-gz-04`）后——这是与 drain 不同的恢复路径，drain 是 K8s 主动优雅驱逐，reboot 验的是"节点宕机后 systemd 开机自启 `k3s-agent`、containerd 自动重建 Pod"——节点 `NotReady→Ready` 多久？其上 Pod 是被原地重启（同 Pod 名、`RESTARTS+1`）还是被驱逐重调度？`k3s-agent` 是否 `enabled`（开机自启是自愈前提）？这是摘除 Compose 老副本后的唯一兜底，故 Phase 10 放行前必须验。
5. **kubectl 定位能力**：四类故障是否都能用 `get pods` / `describe` / `rollout status` / `get nodes` 定位根因？定位命令本身有没有踩坑？

## 3. 演练步骤

三类演练均在 bj-01 执行（`export KUBECONFIG=~/.kube/k3s-ruoyi.yaml`），目标集群为 K3s `ruoyi` namespace。

### 演练 ① — ImagePullBackOff（发布不存在的 tag）

| 要素 | 内容 |
|---|---|
| ① 步骤目标 | 验证发布不存在镜像时旧副本不受影响、新 Pod 卡在拉取失败、undo 可恢复 |
| ② 节点 | bj-01（操作）/ 集群 ruoyi ns |
| ③ 具体命令 | `kubectl -n ruoyi set image deployment/ruoyi ruoyi=100.118.69.78:5000/ruoyi:nonexistent-tag` → `kubectl -n ruoyi get pods` → `kubectl -n ruoyi describe pod -l app=ruoyi`（定位）→ `kubectl -n ruoyi rollout undo deployment/ruoyi`（恢复）|
| ④ 观察窗口 | `kubectl -n ruoyi get pods` 的 STATUS 列 |
| ⑤ 期望现象 | 新 Pod `ImagePullBackOff`；2 个旧 Pod 始终 Running；undo 后恢复 |
| ⑥ 异常退出条件 | 旧副本被提前摘除导致就绪副本 < 1 → 立即 undo |

### 演练 ② — readinessProbe 配错端口

| 要素 | 内容 |
|---|---|
| ① 步骤目标 | 验证 readiness 失败时新 Pod 不接流量、rollout 卡住、旧副本不被摘、undo 可恢复 |
| ② 节点 | bj-01（操作）/ 集群 ruoyi ns |
| ③ 具体命令 | `kubectl -n ruoyi patch deployment ruoyi --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/tcpSocket/port","value":9999}]'` → `kubectl -n ruoyi rollout status deployment/ruoyi --timeout=60s` → `kubectl -n ruoyi get pods` → `kubectl -n ruoyi rollout undo deployment/ruoyi` |
| ④ 观察窗口 | `rollout status` 输出 + `get pods` 的 READY 列 |
| ⑤ 期望现象 | `rollout status` 60s 超时；新 Pod `Running` 但 `READY 0/1`；2 旧 Pod 仍 Running；undo 恢复 |
| ⑥ 异常退出条件 | 就绪副本 < 1 → 立即 undo |

### 演练 ③ — drain worker 节点

| 要素 | 内容 |
|---|---|
| ① 步骤目标 | 验证 drain 驱逐 Pod 后的重调度行为与单副本窗口期，确认不落 control-plane |
| ② 节点 | bj-01（操作），目标 worker `ops-lab-gz-04` |
| ③ 具体命令 | `kubectl drain ops-lab-gz-04 --ignore-daemonsets --delete-emptydir-data --timeout=120s` → `kubectl -n ruoyi get pods -o wide` → `kubectl uncordon ops-lab-gz-04` |
| ④ 观察窗口 | `get pods -o wide` 的 NODE / STATUS 列；`kubectl get nodes` 的 SchedulingDisabled |
| ⑤ 期望现象 | gz-04 上 Pod 被驱逐；替换 Pod 落 gz-06 或 `Pending`，**不落 gz-05**；uncordon 后恢复跨节点分布 |
| ⑥ 异常退出条件 | 替换 Pod 调度到 control-plane gz-05 → 立即记录并排查 affinity |

### 演练 ④ — reboot worker 节点（冷启动自愈）

| 要素 | 内容 |
|---|---|
| ① 步骤目标 | 验证突发宕机 + 冷启动后 Pod 经 `k3s-agent` 开机自启 + containerd 自动重建恢复，确认 Phase 10 摘 Compose 后仍有自愈兜底 |
| ② 节点 | bj-01（操作），目标 worker `ops-lab-gz-04`（reboot） |
| ③ 具体命令 | `kubectl get nodes -o wide` + `kubectl -n ruoyi get pods -o wide`（记基线）→ `ansible gz-04 -m reboot --become`（突发重启，模块等节点重新 SSH 可达再返回）→ `kubectl get nodes -o wide` → `kubectl -n ruoyi get pods -o wide -w`（等 gz-04 Pod 回 1/1）→ `ansible gz-04 -m shell -a 'systemctl is-enabled k3s-agent; systemctl is-active k3s-agent' --become` |
| ④ 观察窗口 | `get nodes` 的 STATUS（NotReady→Ready）；`get pods -o wide` 的 NODE / STATUS / RESTARTS / IP 列；`k3s-agent` enabled/active |
| ⑤ 期望现象 | gz-04 `NotReady→Ready`；其上 Pod **原地重启**（同 Pod 名、`RESTARTS+1`、新 Pod IP），非被驱逐重调度；gz-06 存活副本全程在线；`k3s-agent enabled + active` |
| ⑥ 异常退出条件 | reboot 后 Pod 长时间不恢复 / `k3s-agent` 未 `enabled`（开机未自起）→ 停在本步，不放行 Phase 10，排查 `journalctl -u k3s-agent` 与 containerd |

### 4.5 演练 ④ reboot 冷启动自愈实测（2026-06-12 16:08–16:11，Phase 10 放行决策时执行）

> 演练 ④ 与 ①②③ 不同会话执行，为 Phase 10「摘除 Compose 老副本」的唯一新增前置耐久项。drain（演练 ③）验的是 K8s 主动优雅驱逐，本演练验的是**突发宕机 + 冷启动**这条不同恢复路径：节点 `reboot` 后 systemd 是否开机自启 `k3s-agent`、containerd 是否自动重建该节点上的 Pod。

**前置基线（16:08，reboot 前实测）**：

| 项 | 实测 |
|---|---|
| Pod 分布 | `jzdsm` 在 `ops-lab-gz-06`（AGE 94m）、`zh4mx` 在 `ops-lab-gz-04`（AGE 66m），均 `1/1 Running`、`restarts=0`（`zh4mx` Pod IP `10.42.2.11`）|
| 资源 | `jzdsm` 2m / 522Mi、`zh4mx` 3m / 533Mi（远低于 1.5Gi limit）|
| 节点 | gz-04 / gz-06 worker、gz-05 control-plane，三节点 `Ready` |

**关键时间轴**：

| 时刻 | 事件 | 现象 |
|---|---|---|
| 16:08:54 | `ansible gz-04 -m reboot --become` | `changed: true / elapsed: 42 / rebooted: true`（模块等节点重新 SSH 可达再返回）|
| 16:09:53 | `kubectl get nodes -o wide` | 三节点已全 `Ready`（gz-04 重启后约 60s 内 rejoin）|
| 16:10:00 起 | `kubectl -n ruoyi get pods -o wide -w` | `jzdsm 1/1 Running 0` 在 gz-06 **全程未受影响**；`zh4mx 0/1 Running 1` 在 gz-04，**Pod 名不变、`RESTARTS 0→1`、IP `10.42.2.11→10.42.2.12`**（containerd 在原节点重建 Pod sandbox，非驱逐重调度）|
| ~16:10:30 | watch 续 | `zh4mx 1/1 Running 1` —— 容器重启 + readiness 通过，gz-04 副本恢复就绪 |
| 16:11:14 | `systemctl is-enabled/is-active k3s-agent`（gz-04）| `enabled` + `active`（开机自启成立，自愈前提满足）|

**核心结论**：

- **恢复路径与 drain 不同，结果也不同**：reboot 后 gz-04 在 ~60s 内 rejoin（早于默认 5min pod-eviction 宽限期），故 `zh4mx` Pod **没有被驱逐到别处或停在 Pending**（对比演练 ③），而是**留在原节点原地重启**——同 Pod 名、`RESTARTS+1`、Pod sandbox 重建拿到新 IP。从 reboot 到双副本就绪 ≈ 1.5 min。
- **`k3s-agent enabled` 是冷启动自愈的硬前提**：systemd 开机自启 → k3s-agent 拉起 → containerd 按 Pod spec 重建容器。实测 `enabled + active`，坐实摘除 Compose 后这条兜底成立。
- **单副本窗口与 §4.4 同性质**：reboot 期间 gz-04 副本短暂不可用，存活副本 `jzdsm`（gz-06）全程在线，属与 drain 同性质的"零冗余"窗口（≈1.5 min）。本次 reboot 演练**未挂公网探针**（见 §6 待改进项），用户视角的"单副本窗口零 5xx"结论沿用 §4.4 探针实证（存活副本健康时 `maxUnavailable:0` + Service endpoint 自动摘除让用户无感）。

## 5. 心得 / 反直觉发现

- **`topologySpreadConstraints` 的 `whenUnsatisfiable: DoNotSchedule` 在 drain 单 worker 时会直接牺牲副本数**：drain gz-04 后，替换 Pod 没有像直觉那样"挤"到 gz-06，而是停在 `Pending`——因为 gz-06 已有 1 副本，再调度会让 `maxSkew:1` 不满足，且 gz-05 是 control-plane 被 affinity 排除。结果是 2 worker 架构下任一 worker 维护期间，ruoyi 只能单副本运行。这是 HA 设计的真实边界，不是 bug。
- **`maxUnavailable:0` 在两类发布故障里表现一致且可靠**：演练①②中旧副本全程在线，坏镜像 / 坏探针都只影响"新 Pod"，老流量零中断，印证了 `maxUnavailable:0 + maxSurge:1` 的"先起新、再撤旧"语义。
- **K8s 节点名是 `ops-lab-gz-04`，不是 inventory 里的 `gz-04`**：drain / uncordon 各踩了一次 `NotFound`。kubectl 操作节点前应先 `kubectl get nodes` 确认真实 node name，inventory 的 Ansible 主机名与 K8s node name 是两套命名。
- **`describe pod ... | grep -A5 -iE 'Events|Failed|Back-off'` 没能捞出根因**：演练①里这条定位命令返回空，`describe` 的事件区格式没匹配到该 grep。直接 `kubectl -n ruoyi describe pod <pod>` 看 Events 段、或 `kubectl -n ruoyi get events --sort-by=.lastTimestamp` 更可靠。
- **单副本窗口对公网零影响（4.4 补测实证）**：drain 造成的 ≈50s 单副本窗口期间，公网探针 305 次全 `200`、无延迟尖刺。"少一个副本"在 `kubectl` / 监控视角很显眼，但在用户视角只要存活副本健康就完全无感——**可用性影响（是否中断）和冗余度影响（能否再扛一次故障）是两件事**，演练前差点把后者当成前者来评估严重性。
- **reboot 与 drain 是两条恢复路径，结果天差地别（演练 ④ 实证）**：直觉容易把"节点没了"一概而论，但 drain 是 K8s 主动删 Pod → 受 `topologySpread DoNotSchedule` 约束停在 `Pending`；reboot 是节点短暂离线 → 若在 5min pod-eviction 宽限期内 rejoin，Pod **留在原节点原地重启**（同名、`RESTARTS+1`、新 sandbox IP），根本不触发重调度。判断"节点故障后副本去哪了"必须先分清是"优雅驱逐"还是"宕机重启"，以及节点多快回来。
- **冷启动自愈的前提是 `k3s-agent enabled` 而非 K8s 层任何配置**：Pod 能在 reboot 后自动回来，靠的是节点 systemd 开机自启 k3s-agent + containerd 重建，属"节点侧"能力。摘 Compose 前验自愈，关键一条是 `systemctl is-enabled k3s-agent` 必须 `enabled`，否则节点重启后 agent 不起、Pod 永远不回。

## 7. 演练自我评价

- **本次演练验证了什么核心假设**：K3s 接管若依后，`maxUnavailable:0 + maxSurge:1` 的滚动发布在坏镜像、坏探针两类故障下都能保证旧副本零中断，`rollout undo` 是可靠的一键回滚手段；节点层面，drain 优雅驱逐与 reboot 突发宕机两条恢复路径均经实测（演练 ③④），后者证明摘除 Compose 老副本后 K3s 仍有"节点重启 → k3s-agent 自起 → containerd 重建 Pod"的冷启动自愈兜底。
- **本次演练否定了什么预设**：原以为 drain 一个 worker 后副本会自动迁到另一 worker 维持 2 副本；实测因 `topologySpreadConstraints: DoNotSchedule` + control-plane 排除，副本会停在 `Pending`，HA 在 2 worker 架构下 drain 期间只剩单副本。
- **如果这是真实故障，当前架构的最大短板是什么**：worker 数量只有 2 个且强制打散，任一 worker 不可用即无冗余；control-plane gz-05 被刻意排除业务，不参与兜底。§4.4 补测进一步把该短板定性为"**零冗余**"而非"立即不可用"——单 worker 维护期间公网仍全程 `200`，前提是另一副本健康；真正的暴露点是这段窗口内"再来一次故障就无副本可用"。
- **可沉淀为后续 review 引用的 3 条工程结论**：①`DoNotSchedule` 是"宁可少副本也不违反分布"的硬约束，与"维护期间保副本数"目标冲突，需按场景取舍；②`maxUnavailable:0` 让发布类故障的爆炸半径恒等于"新 Pod"，与节点类故障的可用性影响要分开评估；③K8s node name 与 Ansible inventory 主机名是两套命名，跨系统操作前必须以 `kubectl get nodes` 为准。
