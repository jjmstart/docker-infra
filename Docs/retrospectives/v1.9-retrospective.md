## 重要技术决策解释（模块一）

**Q：为什么选全离线 airgap，而不是 `INSTALL_K3S_MIRROR=cn`、`INSTALL_K3S_ARTIFACT_URL` 改源或在线安装这些更轻的折中？**

A：先看不这么做会怎样。在线安装在 gz 节点踩了两层不可逾越的墙：① 二进制：官方 `get.k3s.io` 脚本从 GitHub 拉 `k3s` 二进制，gz 跨境慢且不稳；② 系统镜像：K3s 一启动，containerd 就要从 `docker.io` 拉 `coredns` / `metrics-server` / `local-path-provisioner`，而 gz 节点对 `docker.io` 实测 `curl` 返回 `000`（连不上）。第二层是关键——很多人以为换个镜像源就行，但 `INSTALL_K3S_MIRROR=cn` 只影响"安装脚本下载二进制"这一步，对"运行时 containerd 拉系统镜像"毫无作用；就算二进制装上了，启动也会卡死在拉镜像。`INSTALL_K3S_ARTIFACT_URL` 能改二进制源，仍然不解决运行时镜像。唯一一招同时覆盖"二进制 + 系统镜像"两段的，就是官方 airgap 镜像包：把 `k3s-airgap-images-*.tar.zst` 预置到 `/var/lib/rancher/k3s/agent/images/`，K3s 首次启动 containerd 自动本地导入，全程不碰 `docker.io`。代价是控制节点要先下产物、跨城拷镜像包（~24min/批），但换来 gz 节点**零公网依赖**、可重复、可离线复现——对一个出网长期受限的节点群，这是确定性最高的方案。

**Q：为什么下载基址走 DaoCloud 代理，而不是直连 GitHub 或 rancher-mirror？**

A：三个源都实测过。直连 `github.com` release CDN：`HEAD` 返回 200 看着通，但 `GET` 卡在 TCP connect 下不完——这是最有迷惑性的，光看 `HEAD` 会误判可用。rancher 的中国镜像 `rancher-mirror.rancher.cn` 对二进制 / airgap 包路径直接 `404`（镜像站没全量同步 release 资产）。只有 DaoCloud 的 GitHub 文件代理 `files.m.daocloud.io/github.com/...` 实测 ranged `GET` 稳定返回 `206` 且能下完。所以判定下载源可用性的标准不是"HEAD 通"，而是"ranged GET 206 且能下完"。实现上把下载基址收敛成单个 `k3s_release_base` 变量，`k3s_version` 是唯一旋钮，恢复直连只需改一行；release tag 里的 `+`（`v1.35.5+k3s1`）在 URL 里转义成 `%2B`。

## 操作心得（模块一）

- **换源先读安装脚本源码**：`mirror=cn` 空操作纯属"想当然"。花 5 分钟读 `get.k3s.io` 源码就能确认它认不认这个变量，避免半天弯路。官方脚本和厂商镜像脚本是两份独立文件，认的环境变量不一样。
- **离线方案要端到端，不止二进制**：airgap 真正的价值在系统镜像包，不在二进制。验收标准要落到"系统 Pod 全 `Running` 且镜像来自本地导入"，而不是"二进制装上了"。
- **下载源用 ranged GET 实测判定**：`HEAD` 200 ≠ 能下完。这次 GitHub CDN 正是"看着通、其实 `GET` 卡死"。`curl -r 0-1023 ... -w '%{http_code}'` 返回 206 才算真可用。
- **幂等哨兵要跟着安装方式走**：二进制改为预置后，`creates: /usr/local/bin/k3s` 会因为二进制先到而误判"已装"跳过安装。离线场景必须把哨兵换成 `install.sh` 真正生成的 `/etc/systemd/system/k3s.service`。
- **粘贴外部内容先查不可见字符**：从网页 / 文档复制的命令容易带入 NBSP / 零宽空格，文本替换会神秘失败。匹配失败别反复试，直接查不可见字符或整段重写。
- **单一旋钮收敛下载源**：把版本、架构、下载基址收敛成 `k3s_version` / `k3s_arch` / `k3s_release_base` 三个变量，升级 K3s 或恢复直连只改一处，URL、缓存路径、校验地址全部派生。

- **决策：Phase 10 的"3 天回滚窗口"校准为"条件放行"**：原 runbook 规定切流后等满 3 天日历窗口再摘老副本。落地时判断该规则的**核心前提在本项目不成立**——3 天窗口在生产环境的价值是"让真实业务流量在多个业务周期里暴露慢性/低频问题"，而 `ruoyi.jjmstart.com` 是零真实流量的学习集群，机械等日历买不到任何流量驱动的验证。故改以一组可验证的放行条件替代日历：Q1 连通（Phase 6）、滚动更新 + 回滚（Phase 8）、三类故障演练（drill §4）、公网探针 drain 单副本窗口 305/305 `200`（drill §4.4）、Q2 内存稳定 + `restarts=0`，以及唯一新增的耐久前置 **reboot 冷启动自愈**（drain 验的是优雅驱逐，reboot 验的是突发宕机 + 冷启动后 k3s-agent 自起、containerd 重建 Pod 这条不同恢复路径，是摘 Compose 后的唯一兜底）。同时把"停 / 删"解耦：`docker compose stop` 零成本、随时拉回，可先做；不可逆的 `down` + `app_nodes` 摘除放到放行条件全绿后。**可迁移结论**：运维"窗口期"的本质是"在新地基被证明耐久前留一条廉价回滚路"，不是"3 这个数字"；当窗口的前提（如真实流量）不成立时，应把日历换成可验证的放行条件，并在文档里记录偏离原因，而非教条等待或无依据跳过。

- **决策（方案 B）：放行验收通过，但 10.3 改为「有界冷备 7 天」而非立即摘除**：2026-06-12 放行条件全绿（reboot 冷启动自愈实测见 drill §4.5：gz-04 reboot 后 Pod 原地重启 ~1.5min 回 1/1、`k3s-agent enabled`），故 Phase 10 放行**判定通过**；执行到 10.2（`stop`）即止，**暂不做不可逆的 10.3**。选择把 gz-02 / gz-03 Compose ruoyi 作为**有界冷备**保留 7 天（至 2026-06-19）：窗口内二者**继续留在 `app_nodes`**（nginx compose 分支遍历 `groups['app_nodes']`，摘 app_nodes 即冷备失效，故必须同进退），ruoyi 维持 `stop`，作为"K3s 控制面 / flannel-over-tailscale **整体**不可用"的逃生舱。**为什么不立即摘除**：放行已证明新地基耐久，K3s 自身的 `rollout undo` + reboot 自愈已能覆盖日常故障；额外留 7 天冷备只是给"控制面整体翻车"这类小概率事件一条廉价兜底，到期即清。**为什么不永久保留**：两个真实代价——① 回滚是**手动三步**（`up -d` → `ruoyi_upstream_target=compose` → 重渲染 nginx），不是 nginx 自动 failover，认知上别把它当"pod 一坏就自动切回"；② Compose 镜像在 `stop` 时刻**冻结**，越往后 K3s 侧发版，冷备拉起来越是旧版本（镜像/配置漂移），冷备会**静默退化成不等价兜底**。永久保留等于长期维护一个会过期的假安全网，违背"讲得清、能排障"。**可迁移结论**：临时回滚兜底要给**明确退役条件 / 时间窗**，否则会从"安全网"漂移成"技术债"——冻结态的备份其等价性随主线迭代单调衰减，这一点对镜像、DB dump、配置快照同样成立。
- **`setup_k3s_app --check` 的 Deployment image 预期内 `changed`（非幂等缺陷，本主题不修）**：Phase 9 经 Jenkins `Build with parameters` 把 ruoyi 镜像钉到具体构建 tag `15-33303b7`（验证滚动更新 + `rollout undo` 回滚）后，线上 Deployment image 即为该 tag，而 `k3s-ruoyi` 模板 `ruoyi_image_tag` 固定 `latest`；`setup_k3s_app.yml --check` 会在 `spec.template.spec.containers[0].image` 检出漂移、稳定报 `changed=1`（其余 ns/configmap/secret/service 四对象 `changed=0`，`--check --diff` 已确认唯一实质差异为 image 字段）。根因是「Ansible 用 `latest` + CI/CD 用精确 tag」双轨制，留待 [`helm-chart-mgmt`](../scheme/phase-1-architecture-upgrade.md#helm-chart-mgmt) 主题统一 tag 注入后消除，本主题不为短期 `changed=0` 做临时 hack。
