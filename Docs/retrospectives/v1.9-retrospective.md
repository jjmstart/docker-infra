## 重要技术决策解释

**Q：为什么选全离线 airgap，而不是 `INSTALL_K3S_MIRROR=cn`、`INSTALL_K3S_ARTIFACT_URL` 改源或在线安装这些更轻的折中？**

A：先看不这么做会怎样。在线安装在 gz 节点踩了两层不可逾越的墙：① 二进制：官方 `get.k3s.io` 脚本从 GitHub 拉 `k3s` 二进制，gz 跨境慢且不稳；② 系统镜像：K3s 一启动，containerd 就要从 `docker.io` 拉 `coredns` / `metrics-server` / `local-path-provisioner`，而 gz 节点对 `docker.io` 实测 `curl` 返回 `000`（连不上）。第二层是关键——很多人以为换个镜像源就行，但 `INSTALL_K3S_MIRROR=cn` 只影响"安装脚本下载二进制"这一步，对"运行时 containerd 拉系统镜像"毫无作用；就算二进制装上了，启动也会卡死在拉镜像。`INSTALL_K3S_ARTIFACT_URL` 能改二进制源，仍然不解决运行时镜像。唯一一招同时覆盖"二进制 + 系统镜像"两段的，就是官方 airgap 镜像包：把 `k3s-airgap-images-*.tar.zst` 预置到 `/var/lib/rancher/k3s/agent/images/`，K3s 首次启动 containerd 自动本地导入，全程不碰 `docker.io`。代价是控制节点要先下产物、跨城拷镜像包（~24min/批），但换来 gz 节点**零公网依赖**、可重复、可离线复现——对一个出网长期受限的节点群，这是确定性最高的方案。

**Q：为什么下载基址走 DaoCloud 代理，而不是直连 GitHub 或 rancher-mirror？**

A：三个源都实测过。直连 `github.com` release CDN：`HEAD` 返回 200 看着通，但 `GET` 卡在 TCP connect 下不完——这是最有迷惑性的，光看 `HEAD` 会误判可用。rancher 的中国镜像 `rancher-mirror.rancher.cn` 对二进制 / airgap 包路径直接 `404`（镜像站没全量同步 release 资产）。只有 DaoCloud 的 GitHub 文件代理 `files.m.daocloud.io/github.com/...` 实测 ranged `GET` 稳定返回 `206` 且能下完。所以判定下载源可用性的标准不是"HEAD 通"，而是"ranged GET 206 且能下完"。实现上把下载基址收敛成单个 `k3s_release_base` 变量，`k3s_version` 是唯一旋钮，恢复直连只需改一行；release tag 里的 `+`（`v1.35.5+k3s1`）在 URL 里转义成 `%2B`。

**Q：为什么把切流后"等满 3 天日历窗口再摘老副本"换成"条件放行"？**

A：3 天窗口在生产环境的价值是"让真实业务流量在多个业务周期里暴露慢性 / 低频问题"，而 `ruoyi.jjmstart.com` 是零真实流量的学习集群——这条规则的**核心前提在本项目不成立**，机械等日历买不到任何流量驱动的验证。故改以一组可验证的放行条件替代日历：Q1 连通（Phase 6）、滚动更新 + 回滚（Phase 8）、三类故障演练（drill §4）、公网探针 drain 单副本窗口 305/305 `200`（drill §4.4）、Q2 内存稳定 + `restarts=0`，以及唯一新增的耐久前置 **reboot 冷启动自愈**（drill §4.5）。reboot 必须单独验是因为它和已验的 drain 是**两条不同的恢复路径**：drain 验的是 K8s 主动优雅驱逐，reboot 验的是"突发宕机 + 冷启动后 systemd 自起 k3s-agent、containerd 重建 Pod"——摘掉 Compose 后这是唯一兜底。实测 gz-04 reboot 后 ~60s `Ready`、Pod 原地重启（同名、`RESTARTS+1`）~1.5min 回 `1/1`、`k3s-agent enabled`，放行判定通过。同时把"停 / 删"解耦：`docker compose stop` 零成本、随时拉回，可先做；不可逆的 `down` + `app_nodes` 摘除放到放行条件全绿后。**可迁移结论**：运维"窗口期"的本质是"在新地基被证明耐久前留一条廉价回滚路"，不是"3 这个数字"；当窗口的前提（如真实流量）不成立时，应把日历换成可验证的放行条件，并在文档里记录偏离原因，而非教条等待或无依据跳过。

**Q：放行已经判定通过，为什么 10.3 仍不立即摘除，而是"有界冷备 7 天"？又为什么不干脆永久保留？**

A：两头都有明确理由。**不立即摘除**：放行证明的是新地基对"日常故障"耐久（发布故障有 `rollout undo`、节点故障有 reboot 自愈），但"K3s 控制面 / flannel-over-tailscale **整体**不可用"这类小概率事件没有集群内手段兜底；把 gz-02 / gz-03 的 Compose ruoyi 以 `stop` 状态多留 7 天（至 2026-06-19），就是给这类事件一条几乎零成本的逃生舱。窗口内二者**继续留在 `app_nodes`**——nginx 的 compose 分支遍历 `groups['app_nodes']`，摘了分组冷备就失效，故必须同进退。**不永久保留**，因为冷备有两个真实代价：① 回滚是**手动三步**（`up -d` → `ruoyi_upstream_target=compose` → 重渲染 nginx），不是 nginx 自动 failover，认知上不能把它当"Pod 一坏就自动切回"；② Compose 镜像在 `stop` 时刻**冻结**，越往后 K3s 侧发版，冷备拉起来越是旧版本（镜像 / 配置漂移），会**静默退化成不等价兜底**。永久保留等于长期维护一个会过期的假安全网，违背"讲得清、能排障"。**可迁移结论**：临时回滚兜底要给明确退役条件 / 时间窗，否则会从"安全网"漂移成"技术债"——冻结态备份的等价性随主线迭代单调衰减，这一点对镜像、DB dump、配置快照同样成立。

| 修完 kubeconfig 错配后流水线再跑，又报 `Failed to import the required Python library (kubernetes) on ef0256811e31's Python /usr/bin/python3` | 上一处修复把 `k8s` 模块执行点从远端 bj-01 改回控制节点，是正确的；但 `kubernetes.core.k8s` 模块要在**执行它的主机**上 `import kubernetes`，执行点现在是 Jenkins 容器，用容器内 `/usr/bin/python3`。Phase 5 当初只在 **bj-01 宿主机**用 `apt install python3-kubernetes` 装了 SDK，Jenkins 镜像（`jenkins-ansible:latest`）的 Dockerfile 只 `pip install ansible`、**没装 `kubernetes`**——`kubernetes.core` collection 随 `ansible` 大包自带，故模块能找到、一 `import kubernetes` 即缺库 | 在 `jenkins-build/Dockerfile` 的 pip 安装里追加 `kubernetes`，重建镜像后 `docker compose up -d --force-recreate` 用新镜像重建容器；`docker exec jenkins python3 -c "import kubernetes"` 验到 `36.0.2`。注意 `restart` 不换镜像，必须 `--force-recreate` | `kubernetes.core` / `community.docker` 这类需要 Python 第三方库的 collection，依赖必须装在**真正执行模块的那个解释器**上：执行点是 Jenkins 容器就装进镜像、是远端被管机就装到被管机。SDK 类依赖固化进镜像（而非流水线临时 pip）；改 Jenkins 镜像后记得 `--force-recreate`，否则容器仍跑旧镜像 |

## 操作心得

- **换源先读安装脚本源码**：`mirror=cn` 空操作纯属"想当然"。花 5 分钟读 `get.k3s.io` 源码就能确认它认不认这个变量，避免半天弯路。官方脚本和厂商镜像脚本是两份独立文件，认的环境变量不一样。
- **离线方案要端到端，不止二进制**：airgap 真正的价值在系统镜像包，不在二进制。验收标准要落到"系统 Pod 全 `Running` 且镜像来自本地导入"，而不是"二进制装上了"。
- **下载源用 ranged GET 实测判定**：`HEAD` 200 ≠ 能下完。这次 GitHub CDN 正是"看着通、其实 `GET` 卡死"。`curl -r 0-1023 ... -w '%{http_code}'` 返回 206 才算真可用。
- **幂等哨兵要跟着安装方式走**：二进制改为预置后，`creates: /usr/local/bin/k3s` 会因为二进制先到而误判"已装"跳过安装。离线场景必须把哨兵换成 `install.sh` 真正生成的 `/etc/systemd/system/k3s.service`。
- **单一旋钮收敛下载源**：把版本、架构、下载基址收敛成 `k3s_version` / `k3s_arch` / `k3s_release_base` 三个变量，升级 K3s 或恢复直连只改一处，URL、缓存路径、校验地址全部派生。
- **"控制节点 == 被管节点"是会掩盖 bug 的特例**：kubeconfig 错配和缺 SDK 两个坑在 bj-01 手动跑都暴露不出来，一上 Jenkins（控制节点是容器）就连环炸。涉及 `delegate_to: localhost` 产物或本地模块依赖的 playbook，必须在"控制节点 ≠ 被管节点"的环境（直接由 Jenkins 触发）验一遍才算验过。
- **可用性影响和冗余度影响是两件事**：drain 单副本窗口在 kubectl / 监控视角很显眼，但公网探针 305 次全 `200`——只要存活副本健康，用户完全无感。该窗口的真实风险是"零冗余"（这 50s 内再来一次故障才会中断），评估严重性时别把"少一个副本"直接等同于"用户受影响"。详见 drill §4.4。
- **节点故障先分清"优雅驱逐"还是"宕机重启"**：drain 触发 K8s 主动删 Pod，受 `topologySpread DoNotSchedule` 约束停在 `Pending`；reboot 后节点若在 pod-eviction 宽限期（默认 5min）内 rejoin，Pod 留在原节点**原地重启**（同名、`RESTARTS+1`），根本不触发重调度。两条路径的恢复行为完全不同，且冷启动自愈的硬前提是节点侧 `k3s-agent enabled`，与 K8s 层任何配置无关。详见 drill §4.5。

## 遗留问题 / 下一步建议

- **冷备窗口到期处置（2026-06-19）**：7 天内 K3s 无重大异常即执行 runbook Phase 10.3——gz-02 / gz-03 `docker compose down`、从 `app_nodes` 摘除，回滚正式改走 K3s `rollout undo`；如期间触发过冷备回滚或发现 K3s 不稳，重置窗口并排查。这是 v1.9 唯一带时限的收尾动作。
- **Deployment image 双轨制（预期内 `changed`，本主题不修）**：Phase 8 经 Jenkins 把镜像钉到精确 tag `15-33303b7` 后，线上 Deployment image 与 `k3s-ruoyi` 模板的 `latest` 漂移，`setup_k3s_app.yml --check` 对 image 字段稳定报 `changed=1`（其余四对象 `changed=0`，`--check --diff` 确认唯一实质差异为 image 字段）。根因是「Ansible 用 `latest` + CI/CD 用精确 tag」双轨制，留待 [`helm-chart-mgmt`](../scheme/phase-1-architecture-upgrade.md#helm-chart-mgmt) 统一 tag 注入后消除，不为短期 `changed=0` 做临时 hack。
- **2 worker + `DoNotSchedule` 的零冗余窗口**：单 worker 维护 / 故障期间 ruoyi 降为单副本（实测公网仍全 `200`，但无再扛一次故障的余量）。处置选项（第 3 worker / 维护期临时放宽 `whenUnsatisfiable` / 接受并写入 SLO）在 worker 拓扑调整时一并评估，见 [`service-migration`](../scheme/phase-1-architecture-upgrade.md#service-migration) 与 drill §6。
- **probe 升级 httpGet**：当前为基线 `tcpSocket:8080`（零依赖、不误判）；确认 RuoYi 健康端点后升级。
- **K3s 缺 Pod / rollout 级监控告警**：当前仅主机层 node-exporter；kube-state-metrics、Pod 重启 / rollout 卡住告警与 Dashboard 留给 [`observability-integration`](../scheme/phase-1-architecture-upgrade.md#observability-integration)。
- **gz 节点 egress 受限是长期事实，建议升级为 review**：`docker.io` / GitHub 不可达不只卡 K3s 安装，后续 [`helm-chart-mgmt`](../scheme/phase-1-architecture-upgrade.md#helm-chart-mgmt)（Helm Chart 拉镜像）、[`loki-logging`](../scheme/phase-1-architecture-upgrade.md#loki-logging)（Loki / Promtail / Alloy 镜像）都会同样撞墙。建议这两个主题落地前，按 docs-workflow §6 单开一份 review，把"K3s 镜像供应链在受限 egress 下的统一策略（私有 Registry 预推 + airgap）"系统化，避免每个主题各自踩一遍。
- **跨城拷贝优化暂不做**：airgap 包 ~24min/批、镜像首拉 ~10.5min 均是一次性成本，引入 rsync / 同城中转 / 同城 Registry 缓存会为没有复发收益的场景加复杂度；若后续频繁重装节点或高频发版再评估。
