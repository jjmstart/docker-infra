## 重要技术决策解释

**Q：为什么 Tailscale IP 回填不继续解析 `tailscale status --json`，而改用 `tailscale ip -4` 加重试？**

A：`tailscale up` 返回成功只代表本机已接受入网配置并开始连接控制面，不代表 `Self.TailscaleIPs` 字段已经立刻出现在 `tailscale status --json` 里。直接解析 status 会遇到短暂时序竞争：节点实际已经入网，但 Ansible 紧接着读取到空 IP 数组，最终打印 `UNKNOWN`。`tailscale ip -4` 是更贴近本步骤目标的命令：Phase 5 真正需要的是可回填 inventory 的 `100.x.x.x` 地址，因此用 `until` 等它返回 `100.` 前缀，可以把"暂时未就绪"变成可控等待，而不是把不完整状态写进操作输出。

**Q：为什么要显式配置 Ansible `remote_tmp`，而不是忽略首次运行的 warning？**

A：这次 `setup_tailscale.yml` 全程 `become: true`，临时目录落到 `/root/.ansible/tmp` 且权限为 `0700` 对当前任务影响不大。但 v1.8 的目标是让 gz-04 / gz-05 后续以 `admin-alex` 非 root 用户登录，再通过 NOPASSWD sudo 提权；如果同一个 play 混用普通用户任务、root become 任务或其他 `become_user`，Ansible 临时模块文件可能因为 root home 下的目录权限不可读而失败。把 `remote_tmp` 固定到 `/tmp/.ansible-tmp` 只是第一步，还需要确保远端目录本身为 `root:root 1777`；否则 Ansible 首次自动创建该目录时仍可能使用 `0700`，非创建者后续无法写入。

## 操作心得

- **`changed=1` 只说明命令执行成功，不等于外部系统状态已完全收敛**：`tailscale up` 返回成功后还需要等待控制面分配 IP；涉及注册、入网、健康检查这类外部状态时，必须增加独立验证步骤。

- **Ansible 的 warning 要按未来连接模型判断影响**：`/root/.ansible/tmp` 或 `/tmp/.ansible-tmp` 的 warning 对当前 root become play 可能不致命，但对后续 `admin-alex` 非 root 登录会变成真实故障。排查 warning 时不要只看"这次有没有失败"，还要看后续架构是否会改变执行身份。

- **`remote_tmp` 要同时管路径和权限**：把路径改到 `/tmp/.ansible-tmp` 只是避免依赖 root home；如果目录被 Ansible 自动创建成 `0700`，问题仍然存在。正确状态是预创建为 `root:root 1777`，让不同连接用户都能创建自己的临时子目录。

- **修 Ansible 自身执行环境时要用 `raw` 做 bootstrap**：普通 Ansible 模块需要先上传到 `remote_tmp` 才能执行，所以不能依赖 `file:` 模块去修坏掉的 `remote_tmp`。`raw` 直接通过 SSH 执行命令，适合放在 `pre_tasks` 里完成最小自举。

- **Docker CLI 比 SDK 适合作为基础设施兜底路径**：当目标是创建网络、检查版本这类简单动作时，CLI 的错误面更小，也更贴近人工排障命令。SDK / collection 适合高层抽象，但一旦遇到 requests / urllib3 兼容问题，排查成本明显高于 CLI。

- **长时间卡住先判断"慢"还是"死"**：apt 安装 Docker 时没有实时进度，但可以观察 `/var/cache/apt/archives/partial` 文件大小、`apt-get` 进程和 HTTPS 连接。只要 partial 文件还在增长，就不是死锁；重复启动 apt 只会引入锁竞争。

- **Jenkins 与本地控制节点不是同一个文件系统**：本地可用的 `~/.ssh/id_ed25519_ansible` 到 Jenkins 容器里不一定存在。inventory 如果需要指定私钥，应优先读取 `ANSIBLE_PRIVATE_KEY_FILE` 这类由 Jenkins credentials 注入的路径，再给本地执行留 fallback。

- **bootstrap 任务要有"已安装则跳过"的边界**：Docker apt repo / GPG key 是从零安装所需，不应在已有 Docker 的老节点上每次全量 check 都访问外网。能力探测比简单 `state=present` 更适合跨新旧节点共用的基础 role。

- **镜像源配置要用拉取行为验证，而不是只看云厂商归属**：gz-04 是百度云节点，但 `mirror.baidubce.com` 在该节点上反而解析失败；能稳定解析并拉取镜像的 mirror 才是有效配置。

- **获取 Tailscale IP 应优先使用 `tailscale ip -4`**：它比解析 `tailscale status --json` 更直接，输出就是 Phase 6 需要回填的 inventory 值；配合 `until` 可以同时覆盖首次接入和已入网重跑两种场景。
